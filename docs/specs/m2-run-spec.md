## 1. 런 구조와 상태 기계

일직선: **일반 전투 5회 + 보스 1회**. `stageIndex` 0..5 (0~4 일반, 5 보스). 갈림길 없음(M4).

### 1.1 상태

```
RunState {
  phase: 'battle' | 'reward_add' | 'reward_edit' | 'victory' | 'defeat',
  stageIndex: number,            // 0..5
  reels: Reel[3],                // 런 시작 시 캐릭터 startingReels의 복사본
  playerHp: number,              // 전투 간 이월
  maxHp: 50,
  offers: ReelSymbol[3] | null,  // reward_add 진입 시 한 번 뽑아 저장. 다시 뽑지 않음(새로고침/재로드로 리롤 불가)
  battle: BattleState | null
}
```

- `BattleConfig.reels = RunState.reels`.
- `createBattle`은 시작 HP를 받아야 한다: `BattleConfig.startingHp?` (생략 시 최대 HP. M1은 항상 최대 HP로 시작했다).
- `k` = 클리어한 전투 수 (1..5). 보상 단계에서 쓴다.
- `N = 3` (삭제/강화 주기, 4장).

### 1.2 전이

| 호출 / 조건 | 결과 |
|---|---|
| `startRun(seed)` | `battle(0)` |
| `battle(i)` 승리 | 회복 적용(3장) 후 `i < 5`이면 `reward_add(k = i+1)`, `i = 5`(보스)이면 `victory` (보상 없음, 회복 없음) |
| `battle(i)` 패배 | `defeat` |
| `reward_add(k)` 선택 또는 건너뛰기 | `k % N == 0`이면 `reward_edit(k)`, 아니면 `battle(i+1)` |
| `reward_edit(k)` 삭제 / 강화 / 통과 | `battle(i+1)` |
| `victory`, `defeat` | 종료 상태. `startRun`만 허용 |

- `N = 3`이므로 삭제/강화 기회는 **전투 3 클리어 후 한 번뿐**이다. 전투 5 클리어 후에는 `reward_add`만 거치고 곧바로 보스(`k = 5`, `5 % 3 != 0`).
- 순서는 항상 **`reward_add` 먼저, 그다음 `reward_edit`**.

### 1.3 이벤트

`battle_won(stage, hpAfter)`, `healed(amount, hpAfter)`, `offers_drawn(offers)`, `symbol_added(reelIndex, symbol)`, `add_skipped`, `symbol_deleted(reelIndex, symbolIndex, symbol)`, `symbol_enhanced(reelIndex, symbolIndex, from, to)`, `edit_passed`, `run_won`, `run_lost(stage)`.

잘못된 호출(단계 불일치, 잘못된 인덱스)은 M1과 같이 **예외를 던진다**.

### 1.4 규칙과 엣지 케이스

| 항목 | 규칙 |
|---|---|
| 승리 직후 | 회복을 즉시 적용한 뒤 `reward_add`. 플레이어 방어도는 전투 간에 이월하지 않는다 |
| 추가 건너뛰기 | 보상 **없음**(골드·게이지 없음). 릴 변화 없음. 이벤트 `add_skipped` |
| 12개 릴에 추가 | 그 릴은 선택 불가(UI 비활성, 엔진은 예외). 세 릴이 모두 12개이면 `reward_add`는 **자동 건너뛰기**(제시 3개를 뽑지 않음, `add_skipped`). **M2에서는 릴이 최대 11개**(시작 6 + 추가 5)까지만 커지므로 이 상한에 걸리지 않는다. 엔진 규칙과 단위 테스트로만 존재 |
| 제시 3개 | 3개의 (동작, 등급) 조합은 서로 모두 다르다. 고른 심볼은 선택한 릴의 **맨 끝**에 추가 |
| 3개 릴에서 삭제 | 불가. 세 릴이 모두 3개이면 삭제 선택지 비활성 |
| 영웅(4)을 강화 | 불가. 등급 4 미만 심볼만 선택 가능. 모두 4이면 강화 선택지 비활성 |
| 삭제·강화 둘 다 불가 | `reward_edit`는 자동 통과(`edit_passed`) |
| 편집 기회 통과 | 허용. 보상 없음 |
| 강화 | 선택한 인덱스 **하나만** 등급 +1, 제자리(크기·순서 불변). 같은 심볼이 여럿 있어도 선택한 인덱스만 변한다 |
| 삭제로 동작이 사라짐 | 릴에서 어떤 동작이 전부 사라져 발동 불가가 되어도 **허용**, 막지 않는다. UI가 편집 전/후 확률을 보여 준다(8장) |
| 패배 | 즉시. 부활·이어하기 없음. 결과 화면용으로 `stageIndex`와 최종 릴을 기록 |
| 재시작 | `startRun(seed)`: 릴은 캐릭터 시작 릴로 초기화, HP 50, `stageIndex` 0, 새 시드. 이월 없음(메타 성장은 M4) |
| 보스 승리 | `victory`. 보상·회복 없음 |
| 시드 | 런마다 rng 하나. 소비 순서는 플레이 순서대로 **전투 스핀(턴당 9회) -> 제시 뽑기(3회)**. 시드와 입력 기록만으로 런 전체가 재현되어야 한다 |

## 2. 보상 심볼 (추가 보상 풀)

후보 = 3개 동작 x 등급 1~4. `weight(a, g) = actionWeight[a] x gradeWeight[k][g]`. 가중치 0인 후보는 제외.

| 동작 | actionWeight |
|---|---|
| attack | 40 |
| guard | 30 |
| shield_bash | 30 |

`gradeWeight[k]` (k = 클리어한 전투 수, 열 = 등급 1/2/3/4):

| k | 1 | 2 | 3 | 4 |
|---|---|---|---|---|
| 1 | 80 | 20 | 0 | 0 |
| 2 | 70 | 28 | 2 | 0 |
| 3 | 55 | 35 | 10 | 0 |
| 4 | 45 | 38 | 15 | 2 |
| 5 | 35 | 40 | 20 | 5 |

- 단계가 진행될수록 높은 등급 확률이 오른다. 영웅(4)은 k = 4부터 등장.
- 스킬 가중치 = 방어 가중치(30)이므로 제시 3개 중 스킬이 1개 이상일 확률이 72~82%.

### 2.1 뽑기 알고리즘 (rng 호출 순서 고정)

1. 후보 목록을 만든다. **바깥 루프 = 동작 순서(attack, guard, shield_bash), 안쪽 루프 = 등급 1->4.** 가중치 0은 건너뛴다.
2. 아래를 **3회** 반복:
   - `total` = 남은 후보 가중치 합
   - `r = rng() x total`
   - 목록을 앞에서부터 보며 `r -= weight`; 처음으로 `r < 0`이 되는 후보를 고른다. 끝까지 가도 안 되면 **마지막 후보**를 고른다.
   - 고른 후보를 목록에서 제거
3. `offers[0..2]` = 뽑은 순서. rng는 정확히 3번 호출한다.

중복은 없다(조합이 모두 다름). 같은 동작의 다른 등급 두 개는 함께 나올 수 있다.

### 2.2 풀 통계 (`node tools/sim/pool-stats.mjs`, 각 10만 회, 실제 출력)

| k | P(공격 >=1) | P(방어 >=1) | P(스킬 >=1) | 최고 등급 평균 | P(최고 >=3) | P(영웅 있음) |
|---|---|---|---|---|---|---|
| 1 | 90.2 | 82.2 | 82.2 | 1.67 | 0.0 | 0.0 |
| 2 | 87.7 | 78.5 | 78.4 | 1.90 | 7.7 | 0.0 |
| 3 | 85.1 | 74.3 | 74.5 | 2.26 | 32.6 | 0.0 |
| 4 | 83.8 | 72.9 | 72.8 | 2.53 | 49.3 | 6.8 |
| 5 | 83.1 | 72.0 | 71.6 | 2.79 | 64.4 | 16.1 |

(몬테카를로 통계라 재실행 시 소수 첫째 자리 안팎의 차이가 날 수 있다. QA 허용 오차는 +-1%p.)

## 3. HP 이월과 회복

- HP는 전투 간에 이월한다. 최대 50.
- 전투 1~4 클리어 후: **+8** (50 상한).
- 전투 5 클리어 후(보스 직전): **+8 대신 전량 회복**(50까지).
- 보스 도중·후에는 회복 없음.
- 이벤트 `healed(amount, hpAfter)`에서 `amount`는 **실제로 늘어난 HP**이다. 0도 허용한다(이미 가득이면 0, 이벤트는 발생).
- 데이터: `healAfterBattle = 8`, `healBeforeBoss = 'full'`.

**근거(탐욕 정책, 1500~2000회)**: 첫 전투 후 회복량별 런 승률: 0 -> 22.1%, 5 -> 46.1%, **8 -> 약 60%(3000회 59.9%)**, 12 -> 70.0%. 보스 직전 전량 회복은 보스를 누적 소모전이 아닌 독립된 시험으로 만든다(전투 5 종료 시 회복 전 탐욕 정책의 평균 HP는 25.2).

## 4. 삭제/강화 주기: N = 3

- 한 번의 기회마다 **하나만 고른다**: 심볼 1개 삭제(릴 최소 3개) **또는** 심볼 1개 +1등급 강화(최대 4) **또는** 통과.
- 기회는 `k % 3 == 0`일 때, 즉 5전투 런에서 **전투 3 클리어 후 한 번**. `reward_add` 다음에 `reward_edit`.

시뮬레이션 (탐욕 정책, 나머지 설정 동일, 2000회. N은 `k % N == 0`인 전투 뒤에 기회):

| N | 기회 | 런 승률 | 빈 턴 비율 | 비고 |
|---|---|---|---|---|
| 1 | 5회 | 96.7% | 전투 4에서 0.0% | 전투당 평균 1.7턴, 릴이 공격 단일로 완전 압축, 사소해짐 |
| 2 | 2회 (전투 2, 4 후) | 74.5% | 전투 5에서 11.8% | |
| **3** | **1회 (전투 3 후)** | **61.0%** | **전투 5에서 16.0%** (보스 14.9%, 3000회) | **채택** |
| 5 | 1회 (전투 5 후) | 50.9% | 전투 5에서 22.5% | |
| 9 | 없음 (추가만) | 43.1% | 전투 5에서 22.3% | |

(N=3의 61.0%는 2000회, 10장의 59.9%는 3000회 결과로 표본이 다르다. 모두 목표 55~70% 안.)

**이유**: GDD 7.3 목표 "보스 직전 잘 짠 릴의 빈 턴 15~20%"에 N = 3이 맞다(약 15%). N = 2는 보스 빈 턴이 한 자릿수로 내려가고 승률 74%, N = 1은 릴이 붕괴한다. 삭제는 추가의 약 2배 효과(GDD 7.3 데이터).
**단점**: 런당 기회가 1회뿐이다. M4의 긴 런에서는 주기에 따라 자동으로 늘어난다. 탐욕 정책은 기회를 낭비하지 않지만 사람은 강화를 고를 수도 있다.

## 5. 스킬 발동률 개선 (3개 일치 규칙은 **그대로, 예외 없음**)

**원인**: 3개 일치 규칙에서는 비율이 낮은 동작이 거의 발동하지 않는다(GDD 8.1). **해법 = 시작 릴 구성 + 보상 풀 가중치**(2장에서 반영).

**시작 릴** (세 릴 모두 동일, 전부 등급 1):
- M1: attack x3, guard x2, shield_bash x1
- **M2: attack x3, guard x1, shield_bash x2**

턴당 정확 확률 (`node tools/sim/reel-stats.mjs` 실제 출력. 40만 회 몬테카를로와 0.1%p 이내 일치):

| | 빈 턴 | 공격 (2라인+) | 방어 (2라인+) | 스킬 (2라인+) |
|---|---|---|---|---|
| M1 | 32.96% | 52.40% (17.37%) | 17.45% (1.01%) | 2.31% (0.00%) |
| **M2** | 32.96% | 52.40% (17.37%) | 2.31% (0.00%) | 17.45% (1.01%) |

- 턴당 스킬 발동 2.3% -> 17.5% (약 7.5배). 전투 1(슬라임)에서 스킬이 한 번 이상 발동할 확률 약 11% -> 약 54%. 빈 턴 비율과 공격은 불변이므로 전투 1의 난이도는 유지된다.
- **부작용(명시)**: 방어 발동이 17.5% -> 2.3%로 줄었다. 문제가 스킬에서 방어로 옮겨 갔다. 완화책: 방패 강타는 하이브리드(등급 합 단위당 피해 1 + 방어도 1)라서 초반 방어를 스킬이 맡고, 순수 방어는 보상 풀(방어 가중치 30)로 키워 가는 심볼이다.
- **위력 상향안은 기각**: 방패 강타 계수(피해 1 / 방어도 1, 합이 공격 계수 2와 같음)를 올리면 발동 시 스킬이 공격·방어를 압도해 빌드 선택이 무너진다. 계수 불변 -> **M1의 방패 강타 데이터는 변경 없음**.
- 런 전체 스킬 발동 (탐욕 정책, 3000회; 스킬 1회 이상 발동 전투 비율 / 턴당 스킬 발동): 전투 1 53.9% / 17.6%, 전투 3 43.9% / 13.6%, 전투 5 32.4% / 12.7%, 보스 37.6% / 11.0%. 탐욕 정책은 공격 쪽으로 압축해 가며 감소하지만 턴당 11~18%를 유지한다.

## 6. 같은 id 효과의 단계 중복 처리 (REQ-002)

**규칙**: 한 동작의 효과 중 **같은 `id`**를 가진 것들은, `minLines <= lineCount`를 만족하는 항목 중 **`minLines`가 가장 큰 하나만** 적용한다. 낮은 단계의 같은 id 항목은 **대체**되며 중첩되지 않는다. **다른 id**는 각각 독립 적용(공격 3라인 = `ignore_guard` **그리고** `weaken`).

- 한 동작 안에 같은 `(id, minLines)`가 둘 이상이면 **데이터 오류**: `createBattle`이 예외를 던진다.
- `maxLines` 필드는 두지 않는다(필드가 늘면 겹침·빈틈 오류가 생김).
- 구현: 순수 함수 `activeEffects(action, lineCount): EffectDef[]`. **모든 효과 실행은 이 함수를 거친다.** M2에서 실제로 실행되는 효과는 `ignore_guard`(`deferred: false`)뿐이지만 `activeEffects`와 테스트는 M2에 포함한다. `deferred: true` 효과는 이전처럼 실행기가 무시한다.
- 데이터 변경: 값 변경 없음. 방어의 `reflect`는 두 항목(`minLines 2 -> percent 30`, `minLines 3 -> percent 50`)으로 유지하고, 이 규칙으로 3라인 이상은 50%만 적용된다. 추가 사항: `(id, minLines)` 중복 검증 + `activeEffects`.

`lineCount` -> 활성 효과:

| 동작 | 1 | 2 | 3 | 4+ |
|---|---|---|---|---|
| guard | 없음 | reflect 30 | reflect 50 (30은 대체됨) | reflect 50 + guard_keep |
| attack | 없음 | ignore_guard | ignore_guard + weaken | ignore_guard + weaken + double_hit |
| shield_bash | 없음 | stun (M3) | stun | stun |

(reflect, weaken, double_hit, guard_keep, stun은 `deferred: true`라 M2에서도 실행되지 않는다.)

## 7. 적과 오우거 힘 모으기

M1 적(슬라임/고블린/해골 병사)은 **변경하지 않는다**(M1 회귀 테스트 보호). 초반용으로 쉬운 변형 두 종을 추가한다(UI가 구별하도록 id와 이름을 다르게).

| stageIndex | 전투 | enemyId | 이름 | HP | 패턴 (순서 반복) | 비고 |
|---|---|---|---|---|---|---|
| 0 | 1 | `slime` | 슬라임 | 24 | attack 5 -> attack 5 -> guard 5 | M1 그대로 |
| 1 | 2 | `goblin_young` | 어린 고블린 | 27 | attack 4 -> attack 8 -> attack 4 | **신규** |
| 2 | 3 | `skeleton_recruit` | 해골 졸병 | 32 | guard 5 -> attack 8 | **신규** |
| 3 | 4 | `goblin` | 고블린 | 34 | attack 5 -> attack 9 -> attack 5 | M1 그대로 |
| 4 | 5 | `skeleton` | 해골 병사 | 40 | guard 6 -> attack 10 | 수치 확정 (M1 명세에서는 "M2 예정") |
| 5 | 보스 | `ogre` | 오우거 | 90 | attack 10 -> charge x2 -> attack 10 -> guard 10 | GDD v0.4의 8 / 16(유효)에서 **10 / 20으로 상향** |

- 변형을 둔 이유: 전투 2~3에서 플레이어 릴이 가장 약하고 HP가 가장 소진된다. M1 수치 그대로면 탐욕 런 승률이 약 43~45%로 떨어진다.
- 오우거 상향 이유: 8 / 16이면 보스 조건부 승률이 약 97%로 시험 구실을 못 했다. 오우거 4턴 주기의 이론 피해 = 10 + 0 + 20 + 0 = 30 (방어도 차감 전).
- 스테이지 목록: `STAGES: EnemyDef[6]` (위 표 순서).

### 7.1 힘 모으기(charge) (M3 상태 시스템 없이 구현)

- `IntentType`에 `'charge'` 추가. `Intent { type: 'charge', value: 2 }`, `value` = 다음 공격에 곱할 배율(정수 2 이상).
- `BattleState.enemyChargeMult` 추가: 기본 1, 전투마다 초기화.
- **적 행동 단계** (M1 명세 2.6의 7단계): 평소처럼 적의 방어도가 먼저 소멸한 뒤:

| 의도 | 처리 |
|---|---|
| `charge` | 피해 없음, 방어도 없음. `enemyChargeMult = value` (덮어쓰기, 누적 없음). 이벤트 `enemy_charged{ multiplier }` |
| `attack v` | `effective = v x enemyChargeMult`. M1의 방어도 흡수/피해 규칙을 `effective`로 적용한 뒤 `enemyChargeMult = 1`. 이벤트 `enemy_attacked`는 `value`(= effective)와 `baseValue`(= v)를 싣는다 |
| `guard v` | 배율을 건드리지 않는다. 힘 모으기는 다음 공격까지 유지된다(오우거 패턴은 쓰지 않음. 엣지 케이스 테스트: 가상 패턴 `[charge x2, guard 5, attack 10]` -> 공격 유효값 20) |

- 힘 모으기 턴에 적이 죽으면(전투 종료) 배율은 의미 없다.
- 플레이어 방어도는 힘 모으기 턴에 쌓아 둘 수 없다(다음 턴 시작에 0). 따라서 **강화된 공격이 나가는 같은 턴에 방어를 만들어 내야 한다**. 이것이 의도한 긴장이다.

### 7.2 의도 미리보기

`intentPreview(state, enemy): { type, value, baseValue, charged: boolean, next?: IntentPreview }`

- `value`: attack = `v x enemyChargeMult`(유효값), guard = v, charge = 배율.
- `baseValue`: 패턴에 적힌 원래 값.
- `charged`: `type == attack && enemyChargeMult > 1`.
- `next`: `type == charge`일 때만 존재. 다음 의도와 그 **유효값**(예: 공격 20).
- UI 예: 힘 모으기 턴 "힘 모으기 -- 다음 공격 x2 (다음: 공격 20)", 다음 턴 "공격 20 (강화됨)".

오우거 결과 (탐욕 정책, 3000회): 평균 4.5턴, 승리 시 남은 HP 평균 27.6, 보스 조건부 승률 84.8%, 전체 런의 10.7%가 보스에서 패배.

## 8. 릴 편집 UI가 엔진에서 받을 수치

숫자만 정의한다(시각 표현은 UI 담당). 모두 **순수 함수, rng 없음, 정확값**(몬테카를로 아님).

```
analyzeReels(reels): {
  empty: number,                       // P(성립 라인 없음), 0..1
  actions: { [actionId]: {
      fire: number,                    // P(해당 동작 라인 >= 1)
      fire2plus: number,               // P(라인 >= 2)
      expectedLines: number,           // 기대 라인 수
      avgGradeValue: number            // 세 릴 전체에서 그 동작 심볼들의 평균 등급 값. 없으면 0
  } },
  reelSizes: [n, n, n]
}
reelComposition(reel): { actionId, grade, count }[]
previewEdit(reels, edit): { before, after }   // 둘 다 analyzeReels 결과
  edit = { kind: 'add', reelIndex, symbol }
       | { kind: 'delete', reelIndex, symbolIndex }
       | { kind: 'enhance', reelIndex, symbolIndex }
```

**방법**: 릴마다, 비복원 3개 뽑기의 **순서 있는 동작 3-튜플**을 열거한다(<= 27 패턴; 순서 있는 인덱스 3-튜플 하나의 확률은 `1 / (n(n-1)(n-2))`이고 같은 패턴끼리 합산). 세 릴의 패턴을 조합(<= 27^3 = 19,683 보드)해 8개 라인을 판정하며 확률을 누적한다. 등급은 라인 성립에 영향이 없으므로 패턴에 넣지 않는다. 참조 구현: `tools/sim/reel-stats.mjs`의 `analyzeReels`.

- 강화는 `fire`/`empty`를 바꾸지 않고 `avgGradeValue`만 올린다(정상 동작이며 버그 아님).
- 어떤 동작의 `fire`가 0이 될 수 있다(예: 한 릴에 그 동작이 없고 다른 릴에는 3개 미만). 0을 반환하고 UI가 보여 주며 편집은 막지 않는다.
- 테스트 허용 오차: 예시값 대비 `1e-9`, 아래 표(%)와 비교할 때는 `0.01%p`.
- 미리보기 범위: 추가 = 제시 3개 x 릴 3개(최대 9가지), 삭제/강화 = (릴, 심볼 종류)별로 서로 다른 경우마다.

**구현된 API (REQ-005 3부, `src/core/reel-analysis.ts`, `run.ts` 기준. 위 시그니처는 개념 표기이고 실제는 아래가 우선)**
- `analyzeReels(reels, options)`: `options = { grades: GradeTable (필수), actionIds?: ActionId[] }`. `grades`는 `avgGradeValue`와 강화 미리보기의 등급 순서에 쓴다. `actionIds`를 주면 어떤 릴에도 없는 동작도 `fire 0`으로 결과에 항상 포함한다(UI가 동작 목록 전체를 보여 줄 때).
- `previewEdit(reels, edit, options)`는 `{ before, after }`. `analyzeEdit(reels, edit, options)`는 편집을 적용한 뒤의 `ReelAnalysis` 하나(`previewEdit`의 `after`와 같다).
- `startRun(definition)`: 시드를 받지 않는다(1.2표의 `startRun(seed)`는 개념 표기). **난수 생성기(`Rng`)는 호출하는 쪽이 소유**하고 `playRunTurn(run, rng)`, `resolveRunTurn(run, board, rng)`(보상 제시를 뽑을 때 rng 사용)에 매번 넘긴다. 엔진 내부에는 전역 난수 상태가 없다.
- `maxHp`는 `RunState`가 `CharacterDef.maxHp`에서 가져온다(`APPRENTICE_KNIGHT.maxHp = 50`). `RunRules`에는 `maxHp`가 없다. 데이터의 단일 출처는 캐릭터 정의.

## 10. 시뮬레이션 결과

`node tools/sim/run-sim.mjs 3000 all` (시드 1). 설정: 시작 릴 AAAGSS x3, N = 3, 회복 +8 / 보스 직전 전량, 보상 풀 2장, 적 7장.

**정책**
- `greedy`: 보상·편집 때마다 모든 후보를 시도(공통 난수, 700스핀)해 점수 = 기대 피해 + 0.7 x 기대 방어도를 가장 올리는 것을 고른다. 아무것도 개선하지 않으면 건너뜀. 편집 기회에는 최선의 삭제/강화를 택한다.
- `takeall`(기준선): 매번 무작위 제시를 무작위 릴에 넣는다. 건너뛰지 않음, 편집 없음.
- `none`: 편집 전혀 없음(참고).

**런 승률**: greedy **59.9%**, takeall 4.7%, none 1.7%.

> **주석 (REQ-005, 2026-11-18)**: 59.9%는 **3,000판, 시드 1** 한 번의 값이다. 실제 엔진 20만 판(QA 포팅)에서는 **약 59%**, 시드별로는 **56.7~59.4%**로 흩어진다. 3,000판의 표준오차는 약 ±0.9%p이므로 "59.9%"를 정확한 목표값이 아니라 56~60% 구간으로 읽는다. 아래 표의 다른 수치(전투별 승률·빈 턴 등)도 같은 3,000판 표본이다. 보스 빈 턴은 20만 판 기준 14.5~14.9%.
> **M2.5 이후**: 이 장은 한 턴 1스핀 규칙의 기록이다. 턴당 다중 스핀 규칙의 재조정 수치는 [`m25-multispin-spec.md`](m25-multispin-spec.md)가 우선한다.

**탐욕 정책의 패배 지점**: 슬라임 0.3%, 어린 고블린 4.0%, 해골 졸병 8.7%, 고블린 10.4%, 해골 병사 5.9%, 오우거 10.7%.

**보스 빈 턴 비율**: greedy 14.9%, takeall 30.4%, none 32.7%.

|---|---|---|---|---|---|---|---|---|

**해석**
- 탐욕 승률 59.9%는 목표 55~70% 안.
- 빈 턴 비율이 32.5% -> 14.9%로 내려간다(GDD 7.3 목표 15~20%; 보스 14.9%는 경계. QA가 20만 회로 확인).
- takeall 4.7%: 무작위 추가는 릴을 묽힐 뿐이다(건너뛰기가 정답일 수 있다는 설계 의도와 일치). 다만 "전부 받는" 플레이어에게는 매우 낮다(12장 4).
- 전투 3 -> 4 사이의 빈 턴 점프(27.5 -> 18.7)는 삭제/강화 기회의 효과다.
- 시뮬레이터의 `goblin_a`, `skeleton_a`, `goblin_b`, `skeleton_b` 등은 내부 표기이고 제품 id는 7장 표를 따른다(`goblin_young`, `skeleton_recruit`, `goblin`, `skeleton`).

**수치 검증 (2026-11-17)**: `node tools/sim/reel-stats.mjs`와 `node tools/sim/pool-stats.mjs`를 실행해 5장 확률표, 예시 1b/2/3 확률, 2.2의 풀 통계가 본 문서와 일치함을 확인했다. `run-config.mjs`의 적·가중치·회복·N·릴 상한도 본 문서와 일치. `run-sim.mjs`(3000회)는 느려서 재실행하지 않고 설계 담당이 준 결과를 옮겼다.

## 12. 미결 사항

| # | 항목 | 내용 |
|---|---|---|
| 1 | 삭제/강화 기회가 런당 1회 | N = 3은 빈 턴 목표에 맞지만 플레이어의 선택 폭이 좁다. N = 2는 승률 74.5%, 보스 빈 턴 한 자릿수로 보스·풀 재조정이 필요. 플레이테스트 후 재검토 |
| 2 | 시작 방어 발동 2.3% | "죽은 심볼"처럼 느껴질 수 있다. 대안: 7개짜리 시작 릴(빈 턴 증가) |
| 3 | 보스 빈 턴 14.9% | 목표 15%와 경계. QA 20만 판 확인 결과 14.5~14.9%. **해결(REQ-005 2부)**: 1스핀 기준 목표는 폐기. 다중 스핀(M2.5)에서는 "스핀 1회가 비는 확률"이 아니라 "턴 전체가 비는 확률(최종 합산이 0)"로 정의가 바뀌며 새 목표는 `m25-multispin-spec.md` 9장 |
| 4 | takeall 4.7% | 제시를 다 받기만 하는 플레이어를 위한 완만한 바닥이 필요한가(건너뛰기 보상, 제시 4개, 초반 스테이지 완화)? 플레이테스트 후 결정 |
| 5 | 탐욕 정책은 대리 지표 | 사람은 비효율적으로 고른다(스킬 빌드 등). 스킬 중심 정책 추가 검토 |
| 6 | 건너뛰기 보상 없음은 잠정 | 탐욕 정책의 건너뛰기 빈도는 측정하지 않음 |

**확정 여부**: M2의 잠정 결정(런 구조, 주기, 회복, 적 수치 등)은 총괄 디렉터가 정한 것이며 **사용자는 아직 확정하지 않았다.** 사용자가 런 구조나 주기를 바꾸면 1, 4, 7, 10장을 `tools/sim`으로 다시 생성해야 한다.
